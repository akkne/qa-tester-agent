# Сценарий от push до отчёта

## Триггер и фиксация диапазона

Workflow запускается только для выбранной исходной ветки, исключает `qa/**` и обновления, состоящие лишь из `revision/**` и иных путей отчётов. Он передаёт `repository`, `branch`, `baseSha` (`before`) и `headSha` (`after`) локальному API на self-hosted macOS runner. Для первого push `baseSha` должен быть явно задан в профиле или входе: нулевой `before` не принимается. Запуск по нескольким коммитам обрабатывает весь диапазон `baseSha..headSha`. Повторная доставка получает прежний `RunId`.

После приёма `headSha` неизменен. Новый push создаёт новый запуск, пока worker продолжает старый. Ветка и результат старого запуска всегда относятся к зафиксированному SHA. Если базовый SHA недоступен после переписывания истории, запуск становится `BLOCKED` с причиной, а не переключается на текущую ветку.

## Этапы worker

1. **Получение.** В отдельном рабочем каталоге fetch точных SHA, checkout `headSha` в detached состоянии, проверка объекта commit. Сбор `git diff baseSha headSha`, изменённых файлов и истории коммитов. Ветка `qa/<short-sha>-<run-id>` создаётся от `headSha` в другой изолированной копии.
2. **Контекст.** Чтение ТЗ из каталога `SpecificationDirectory` профиля (для `demo` — `docs/qa`), diff, изменённых производственных исходников, существующих тестов и настроек сборки. Секреты удаляются или маскируются до LLM. Неизменённый исходник не передаётся модели; если его не хватает для вывода, фиксируется недостаток контекста.
3. **План.** LLM связывает ID требований с изменённым поведением, составляет позитивные, негативные, граничные и access-control сценарии. Неясное ТЗ помечается отдельно. Ответ проверяется JSON-схемой и лимитами.
4. **Анализ.** Проверка соответствия ТЗ, ошибок, валидации, доступа, утечек данных и типовых инъекций. Для каждого замечания нужны файл/строка, ожидаемое поведение, гипотеза и способ воспроизведения. Сканер секретов работает отдельно.
5. **Тесты.** Генерация тестов только для новой/изменённой функциональности в разрешённых тестовых путях. Проверка diff запрещает правку исходного кода, удаление проверок, `Skip` и подгонку ожидаемого результата. До двух попыток исправления разрешены лишь для синтаксиса, компиляции или ошибки тестового окружения; падающий корректный тест сохраняется.
6. **Исполнение.** Сборка и весь существующий плюс новый набор тестов в контейнере. Сбор результатов и Coverlet line coverage, включая покрытие исполняемых изменённых строк (где режим исполнения профиля это поддерживает).
7. **Браузер.** Запуск стенда из того же `headSha` с синтетическими данными, healthcheck, Chromium desktop и один мобильный viewport. Playwright открывает страницы, вводит данные и проверяет результат. При сбое сохраняются screenshot, console/network errors и trace.
8. **Публикация.** Формирование `revision/commit_<short-sha>.md`, commit только тестов и отчёта, push QA-ветки, ссылка в API/UI. Если публикация не удалась, запуск `BLOCKED`, локальный отчёт остаётся доступным. QA-ветка публикуется и тогда, когда LLM-тесты были исключены: в ней остаётся только отчёт.
9. **Итог в GitHub Actions.** Job `qa` ждёт завершения запуска (до 90 минут), пишет в Job Summary статус, проверки, ссылки на QA-ветку, отчёт и локальную страницу, а также полный Markdown-отчёт. `PASSED` — зелёный job, `FAILED` и `BLOCKED` — красный с причиной в аннотации. Ручной `workflow_dispatch` по умолчанию запускает новую попытку.

Страница результата `GET /runs/{id}` и ссылки на локальные артефакты открываются на loopback API с HTTP Basic: пароль — ключ `AgentApi__Key`. JSON API продолжает использовать `X-Agent-Key`. Отчёт в GitHub ссылается на локальную страницу, поэтому screenshot и trace доступны на MacBook с запущенным сервисом.

Лимиты времени (`Agent:RunTimeoutMinutes`, `StageTimeoutMinutes`, `AnalysisTimeoutMinutes`) читаются из конфигурации; число попыток исправления тестов (две) и префикс QA-ветки `qa/` заданы в коде. После каждого этапа сохраняется состояние, чтобы ошибка или рестарт были видны пользователю.

## Git-правила

- Проверяемый диапазон и тестовый стенд связаны с `headSha`, не с движущимся именем ветки.
- `qa/**` не вызывает workflow. Изменение только отчётов не вызывает новую проверку; смешанный push с кодом проверяется.
- QA-ветка содержит только новые/изменённые тесты и `revision/`; скриншоты и traces остаются в локальном хранилище и доступны через страницу результата.
- Имя QA-ветки включает `run-id`, чтобы два запуска одного SHA не сталкивались. Публикация повторного этапа сверяет существующий commit перед push.
- До коммита агент выполняет полный набор проверок проекта и не коммитит секреты или реальные `.env`.

Справка: [GitHub push event payload](https://docs.github.com/en/webhooks/webhook-events-and-payloads#push), [workflow filters](https://docs.github.com/en/actions/writing-workflows/workflow-syntax-for-github-actions#onpushbranchesbranches-ignore).
