# Безопасность MVP

MVP обрабатывает один заранее доверенный приватный репозиторий. Тем не менее код, ТЗ, diff и ответы LLM считаются недоверенными данными. Они не могут менять системные правила агента, команды профиля или разрешённые пути записи.

## Границы исполнения

- Оркестратор хранит GitHub/LLM/API ключи на хосте и управляет Docker. Контейнеры приложения и тестов не получают эти ключи, домашнюю папку хоста или Docker socket.
- Контейнеры получают только нужный checkout, тестовую БД и синтетические данные. Для каждого запуска используются отдельные имена ресурсов, ограничения времени, CPU, памяти и очистка после завершения.
- Команды сборки, тестов, стенда и healthcheck берутся из проверенного профиля. LLM не создаёт shell-команды для исполнения.
- Запись тестов разрешена только в тестовых каталогах профиля, отчёта — только в `revision/`. Путь нормализуется и проверяется относительно корня checkout; симлинки и обход `..` не расширяют границу.
- Находки о правах доступа, раскрытии чувствительных полей, валидации и типовых инъекциях формируются в рамках изменённого поведения. Секреты сканирует отдельный детерминированный сканер.

## Секреты и данные

Секреты и внешние идентификаторы хранятся в локальных `.env.<environment>`, которые игнорируются Git. Перед отправкой контекста LLM и записью логов, Markdown или артефактов значения маскируются. Проверка перед commit отбрасывает реальные `.env`, ключи и подозрительные значения. Тестовые аккаунты и данные синтетические; production-учётные записи не используются.

API доступен только через loopback и требует ключ от runner. Ссылки на артефакты используют ID и проверку пути; HTML экранирует недоверенный текст. На Linux-сервере потребуется отдельное решение для TLS и удалённого доступа до открытия API наружу.
