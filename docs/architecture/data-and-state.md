# Данные, очередь и статусы

## Модель PostgreSQL

| Сущность | Ключевые поля |
| --- | --- |
| `Run` | `Id`, `RepositoryId`, `ProfileVersion`, `BaseSha`, `HeadSha`, `Trigger`, `State`, `FinalStatus`, `CreatedAt`, `StartedAt`, `FinishedAt`, `QaBranch`, `ReportPath`, `FailureReason` |
| `RunStage` | `RunId`, `Name`, `State`, `Attempt`, `StartedAt`, `FinishedAt`, `ErrorCode`, `Summary` |
| `Finding` | `RunId`, `RequirementId`, `Severity`, `EvidenceKind`, `File`, `Line`, `Expected`, `Actual`, `Reproduction`, `ArtifactIds` |
| `TestCandidate` | `RunId`, `Path`, `ContentHash`, `RequirementIds`, `QaBranch`, `State`, `AcceptedInSha` |
| `Artifact` | `RunId`, `Kind`, `LocalPath`, `PublicPath`, `Checksum`, `CreatedAt` |
| `LlmUsage` | `RunId`, `Stage`, `Model`, `InputTokens`, `OutputTokens`, `EstimatedCost` |

`Run` одновременно служит элементом очереди. Создание запуска и запись ключа идемпотентности выполняются одной транзакцией через `IUnitOfWork`. Уникальный ключ: `(RepositoryId, BaseSha, HeadSha, ProfileVersion)` для автоматических push. Повторная доставка того же push возвращает прежний `RunId`. Ручной повтор имеет отдельный `Trigger` и явный `RerunOfRunId`.

Один worker атомарно захватывает самый старый `Queued` запуск и переводит его в `Running`. Этапы сохраняются после каждого шага; на рестарте незавершённый запуск либо восстанавливается с безопасного контрольного пункта, либо завершается `BLOCKED` с объяснением. Побочные действия, включая push, повторяются идемпотентно по стабильному имени ветки и проверке commit SHA.

## Состояние процесса и итог

Состояние процесса: `Queued → Running → Completed`. При невозможности завершить процесс фиксируются `Completed/BLOCKED` и причина. Итоговый статус вычисляется после всех обязательных этапов:

| Итог | Условие |
| --- | --- |
| `PASSED` | Все обязательные этапы и тесты завершились успешно; нет воспроизведённых проблем или открытых неоднозначностей |
| `FAILED` | Есть воспроизведённая ошибка или упавший корректный тест |
| `NEEDS_REVIEW` | Есть только неподтверждённые замечания/неоднозначное ТЗ при завершённых обязательных проверках |
| `BLOCKED` | Обязательный этап не завершён: окружение, API/LLM, контекст, таймаут, генерация тестов, недоступный стенд |

При нескольких условиях приоритет `BLOCKED`, затем `FAILED`, затем `NEEDS_REVIEW`, затем `PASSED`; отчёт перечисляет все известные находки независимо от итога. Ошибка генерации и недоступный браузер никогда не дают `PASSED`.

## Тесты-кандидаты

Новый тест появляется в QA-ветке со статусом `Proposed`. Кандидат переходит в `Accepted` только после проверки его содержимого или явно принятого эквивалента в исходной ветке; совпадение одного пути недостаточно. Следующий запуск исполняет тесты из нового `headSha` и отдельно показывает открытых кандидатов предыдущих запусков; не копирует их молча в checkout и не объявляет принятыми. Для презентации разработчик принимает QA-ветку, поэтому второй push уже содержит эти тесты.
