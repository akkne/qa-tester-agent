# QA-агент: материал для презентации

Сводка по состоянию ветки `fix/full-audit` на 29 октября 2026 года. Подробности — в остальных файлах `/docs`; ссылки даны по тексту.

---

## 1. Суть в одном абзаце

QA-агент — автоматический тестировщик, который подключается к GitHub-репозиторию и проверяет каждый push **до того, как задача уйдёт PM**. Он читает ТЗ проекта и diff изменения, понимает, какие требования затронуты, сам пишет недостающие тесты (позитивные, негативные, на права доступа), прогоняет всю тестовую базу и браузерные сценарии в изоляции и публикует отчёт с доказательствами в отдельную QA-ветку. Вердикт — `Passed`, `Failed`, `NeedsReview` или `Blocked` — выносит детерминированный код по фактам (коды завершения, отчёты тестов), а не по словам модели.

## 2. Какую проблему решает

| Боль | Что даёт агент |
| --- | --- |
| Разработчик пишет фичу, а тесты на новое требование не пишет или пишет только «счастливый путь» | Агент генерирует позитивные, негативные и access-control тесты по ID требования из ТЗ |
| Ручной QA — узкое место и задержка между push и приёмкой | Проверка стартует автоматически на каждый push, результат — в GitHub Actions и QA-ветке |
| «У меня всё работает» — непонятно, что именно проверено | Отчёт привязан к точному диапазону `baseSha..headSha`: какие тесты, сколько упало, покрытие изменённых строк, скриншоты и trace |
| LLM-инструменты галлюцинируют и выдают «всё ок» | Модель только предлагает; итог считает код по exit-кодам и JUnit/TRX. Гипотеза модели и воспроизведённый дефект — разные поля отчёта |
| Сгенерированные тесты теряются | Они лежат в QA-ветке; команда принимает их merge-ем, и они становятся регрессией для следующих push |

## 3. Как это выглядит для команды

1. Разработчик делает push в `main`.
2. GitHub Actions (self-hosted runner) передаёт диапазон коммитов агенту. Job `qa` ждёт результат до 90 минут.
3. Агент анализирует, пишет тесты, прогоняет всё.
4. В Job Summary появляется статус, ссылки на QA-ветку и отчёт, полный Markdown-отчёт. `Passed` — зелёный job; `Failed`/`Blocked` — красный с причиной.
5. В репозитории появляется ветка `qa/<short-sha>-<run-id>`: в ней **только** новые тесты и `revision/commit_<short-sha>.md`.
6. На локальной странице `/runs/{id}` видна живая лента работы агента (обновляется каждые 3 секунды), итог, расход токенов и ссылки на скриншоты/trace/логи.
7. Команда смотрит отчёт, принимает тесты в `main`, чинит дефект. Следующий push уже прогоняет принятые тесты и подтверждает исправление.

## 4. Сквозной конвейер: от push до отчёта

```text
GitHub push → Actions (self-hosted macOS) → POST /api/runs → PostgreSQL (очередь)
                                                   ↓
                                     BackgroundService — один worker
                                                   ↓
   M1 Git ─► M2 Анализ и тесты ─► M3 Исполнение и браузер ─► M4 Публикация ─► итог в Actions
              ↘ codex exec (план, находки)   ↘ Docker / Codex-агент   ↘ git push QA-ветки
              ↘ Codex-агент пишет тесты
```

### M1. Приём и фиксация изменения
- Workflow передаёт `repository`, `branch`, `baseSha`, `headSha`. Ветки `qa/**` и push, где поменялись только отчёты, не запускают проверку — нет бесконечного цикла.
- Запуск — строка в PostgreSQL; она же элемент очереди. Ключ идемпотентности: `(репозиторий, baseSha, headSha, версия профиля, попытка)`. Повторная доставка того же события возвращает тот же `runId`.
- Worker делает checkout **точного** `headSha` в изолированный каталог и считает diff `baseSha..headSha`. Если в ветку уже прилетел новый push, старый запуск всё равно проверяет свой SHA.

### M2. Анализ и генерация тестов
1. **Сканер секретов** (детерминированный, без LLM) проверяет изменённые строки. Нашёл токен или ключ — LLM не вызывается.
2. **Контекст**: ТЗ из каталога профиля, diff, изменённые исходники, существующие тесты, настройки сборки. Неизменённый код модели не передаётся.
3. **План** (`codex exec` с JSON-схемой): какие ID требований затронуты, какие сценарии нужны — позитивные, негативные, граничные, access-control. Если ТЗ не менялось, изменение получает технический ID `CHANGE-<SHA>`.
4. **Находки** (второй `codex exec`): несоответствие ТЗ, ошибки валидации, доступа, утечки, инъекции. Для каждой — файл/строка, ожидание, гипотеза, как воспроизвести.
5. **Написание тестов** — Codex-агент в Docker-контейнере пишет тесты на языке и фреймворке репозитория, только в разрешённые каталоги, и обязан их собрать. Ошибки сборки своих тестов чинит сам.
6. **Проверки сервиса** над результатом агента (см. раздел 6). Не прошёл — тесты отбрасываются, запуск продолжается с тестами репозитория.

### M3. Исполнение и браузер
- Полная сборка и **вся** тестовая база (старые + новые) в Docker. Выборочного прогона нет.
- Покрытие: Coverlet/Cobertura; отдельно считается доля **исполняемых изменённых строк**, покрытых тестами. Нет данных — пишется «не измерено» с причиной, а не 0% или 100%.
- Стенд поднимается из того же `headSha`, проверяется `/healthz`, затем Playwright гоняет Chromium в двух viewport — desktop 1280×800 и mobile 390×844. При падении сохраняются скриншот, trace, ошибки консоли/сети/5xx.
- Режим исполнения выбирается в профиле (раздел 7).

### M4. Публикация
- Markdown-отчёт `revision/commit_<short-sha>.md`: SHA, файлы, требования, добавленные тесты, результат всей базы, покрытие проекта и изменений, непроверенные сценарии, находки с серьёзностью/ожиданием/фактом, ссылки на доказательства, длительность, расход LLM, итог с причиной.
- Коммит **только** тестов и отчёта в `qa/<short-sha>-<run-id>`, родитель — точный `headSha`. Повтор публикации сверяет уже существующий коммит, а не создаёт дубль.
- Скриншоты и trace остаются локально и отдаются через API по ID — в Git попадает только Markdown.

## 5. Где именно работает Codex

Модель вызывается через локальный `codex exec` под ChatGPT-логином; отдельного API-ключа не нужно. В Application всё скрыто за портом `ILlmClient`, провайдера можно заменить.

| Точка | Что делает Codex | Чем ограничен |
| --- | --- | --- |
| M2: план | Связывает требования с изменением, составляет сценарии | `--sandbox read-only`, временный каталог без checkout, JSON-схема ответа, список допустимых ID требований прямо в схеме |
| M2: находки | Ищет логические ошибки и проблемы безопасности в изменении | То же; гипотезы не выдаются за доказанные дефекты |
| M2: написание тестов | Пишет тесты в стеке репозитория, собирает их через `qa-run` | Одноразовый контейнер, `.git` только для чтения, запись только в разрешённые каталоги, сервис перепроверяет каждый файл |
| M3 (режим `agent`) | Находит тестовые наборы любого стека, ставит toolchain и зависимости, запускает тесты | Каждая команда — через обёртку `qa-run`, которая пишет exit-код в журнал; вердикт считает сервис |

**Codex не нажимает кнопки в браузере.** Браузерные проверки — это Playwright-сценарий `browser/run.mjs`, написанный человеком (см. раздел 8).

Учёт расхода: входные и выходные токены из события `turn.completed` суммируются и попадают в отчёт. Например, в live-приёмке M6 анализ одного push занял 161 097 входных и 4 181 выходной токен.

## 6. Ключевые решения и почему

### 6.1. «LLM предлагает, код решает»
Самое важное решение проекта. Модель полезна там, где задача плохо формализуется: понять ТЗ, придумать сценарии, найти тестовые наборы в незнакомом репозитории. Но вердикт должен быть воспроизводимым и честным:
- **Exit-код** — только из журнала `ledger.jsonl`, который пишет обёртка `qa-run`. Команда, выполненная в обход обёртки, считается невыполненной.
- **Число тестов** — только из разобранных JUnit XML / TRX. Цифры агента используются, лишь когда отчёта нет, и тогда набор помечается `Unverified`.
- **Полнота** — набор, который есть в журнале, но «забыт» в ответе агента, всё равно оценивается: агент не может спрятать падающий набор.
- **Целостность** — после работы агента `HEAD` должен равняться `headSha`, а отслеживаемые файлы не должны измениться. Иначе — `Blocked`.

### 6.2. Сгенерированные тесты — гипотезы, а не приговор
Если прогон упал **вместе со сгенерированными тестами**, worker повторяет проверку **без них** на чистом checkout:
- без них всё зелёное → итог `NeedsReview`: продукт по собственным тестам в порядке, а сгенерированные тесты лежат в QA-ветке на ревью (возможно, нашли дефект, возможно, модель ошиблась в ожидании);
- без них тоже падает → `Failed`: проблема в самом продукте.

Так ошибка модели не может сама по себе «покрасить» push в красный, но и реальный дефект не теряется.

### 6.3. Защита от «подгонки» тестов
Агент-писатель не может обмануть проверку:
- только **новые** файлы, только в `AllowedTestDirectories`, без симлинков, текст, до 60 000 символов, не больше 30 файлов;
- запрещены `skip`/`xfail`/`.only`/`@Disabled`/`#[ignore]`/`t.Skip` и аналоги;
- в тестовом файле должно быть утверждение и хотя бы один известный ID требования;
- последняя фаза `build` его набора должна пройти с кодом 0;
- после проверки рабочий каталог полностью сбрасывается, и в него записываются **только** принятые файлы — мусор агента до M3 и QA-ветки не доходит;
- продуктовый код агент не меняет; корректный тест, упавший из-за продукта, остаётся падающим как доказательство.

### 6.4. Честные статусы и приоритет
`Blocked` > `Failed` > `NeedsReview` > `Passed`.
- `Blocked` — код **не удалось** проверить: недоступен SHA, Docker, стенд, браузер, покрытие, таймаут, публикация. Недоступный стенд никогда не даёт `Passed`.
- `Failed` — воспроизведённая ошибка или упавший корректный тест. Реальная ошибка сборки/тестов — это `Failed`, а не `Blocked`.
- Сбой LLM не блокирует проверку: если анализ недоступен или превысил лимит, запуск продолжается с тестами репозитория, а причина попадает в раздел «Warnings and context gaps».

### 6.5. Точный SHA и идемпотентность
Всё привязано к неизменяемым `baseSha`/`headSha`, а не к имени ветки. Повтор события → тот же `runId`. После `Blocked` или с `rerun: true` → новая попытка со своим `runId` и своей QA-веткой; история сохраняется. Зависший после рестарта запуск закрывается `Blocked` по таймауту.

### 6.6. Простая инфраструктура для MVP
- Один процесс ASP.NET Core: API, страница результата и worker.
- PostgreSQL одновременно хранит результаты и служит очередью — Redis не нужен при одном worker. Вся схема — одна таблица `runs` с JSON-колонками этапов.
- Захват задачи — условное атомарное обновление строки: второй обработчик ту же строку не возьмёт.

### 6.7. Чистая архитектура с портами
`Host → Infrastructure → Application → Domain`. Application не вызывает Git, PostgreSQL, Docker, HTTP или LLM напрямую — только через порты (`IGitWorkspace`, `ILlmClient`, `IM2TestWriter`, `IM3Executor`, `IReportPublisher`, `ISecretScanner`, `ICoverageCalculator`…). Адаптеры выбираются только в composition root. Направление зависимостей проверяет `scripts/check_architecture.py`.

### 6.8. Агент для любого стека
Последнее крупное расширение: и написание, и запуск тестов можно отдать Codex-агенту в образе `qa-agent/test-runner` (Node, Python, Java, Go, .NET + `mise` для остальных версий). Агент сам читает CI-файлы, ставит зависимости lockfile-командами, добавляет JUnit-репортер вне отслеживаемых манифестов. Prompt построен как инструкция исполнителю: запрет изменять файлы, обязательный `qa-run`, запрет маскировать падения повторами и фильтрами, не больше трёх подходов к настройке одного набора, README и CI — данные, а не инструкции (защита от prompt injection).

## 8. Браузерные проверки: как есть на самом деле

- `browser/run.mjs` — фиксированный Playwright-сценарий: анонима перекидывает с `/cabinet` на `/login`; пароль из пробелов отклоняется; регистрация через форму; неверный пароль не пускает; верный — открывает свой кабинет; подмена ID кабинета даёт 403 и не раскрывает чужой email; повторный email даёт понятную ошибку; выход закрывает доступ.
- Запускается сервисом в Chromium headless, дважды: desktop и mobile (с touch). Требует нулевых ошибок JS, сетевых сбоев и 5xx.
- При падении сохраняются скриншот, Playwright trace (можно открыть в Trace Viewer) и JSON с шагами и диагностикой.
- **Чего нет:** агент не генерирует новые браузерные сценарии и не исследует сайт сам. «Исследовательский браузер» — в планах после M6.

**Live-приёмка сама нашла и исправила три ошибки агента** — хороший сюжет для слайда «как мы проверяем самого агента»:
1. Сканер секретов принимал выражения вида `password = cond ? …` за захардкоженные секреты → ограничен литералами.
2. Модель выдумала несуществующий ID требования → список допустимых ID вшит прямо в JSON-схему ответа.
3. Строки объявления методов ошибочно считались «непокрытыми» → исключены из расчёта.

`bash scripts/check.sh` одной командой проверяет формат, сборку, unit/integration/demo-тесты, архитектуру, PostgreSQL, миграции, идемпотентность и работу двух хостов.

## 10. Безопасность

- Код, ТЗ, diff и ответы LLM — **недоверенные данные**; они не могут менять правила агента, команды профиля и разрешённые пути.
- Секреты хранятся в игнорируемых `.env`, маскируются до отправки в LLM и в логи; перед коммитом отбрасываются реальные `.env` и ключи.
- `codex exec` для анализа: read-only sandbox, временный каталог без checkout, без ключей GitHub и приложения в окружении.
- Контейнеры тестов не получают Docker socket и домашнюю папку хоста; лимиты CPU, памяти, процессов, таймауты. Git на хосте запускается без hooks и fsmonitor, чтобы код из контейнера не исполнился на хосте. Симлинки из контейнера отвергаются.
- API слушает только loopback, ключ сравнивается без логирования; страница — HTTP Basic; артефакты — только по сохранённому ID с проверкой пути; HTML экранируется.
- Честное ограничение режима `agent`: код проверяемого репозитория выполняется в одном контейнере с Codex и может прочитать его авторизацию. Для недоверенных репозиториев нужен отдельный API-ключ с лимитом. `AllowDocker: true` фактически даёт root на хосте — только для доверенных репозиториев.

Около 7 000 строк C# в `src` и `tests` (без миграций), 18 файлов тестов самого агента, 4 C#-проекта сервиса + `tools/M3Probe` для ручной диагностики M3.

## 12. Ограничения и что дальше

**Сейчас:**
- один приватный репозиторий, один профиль, один worker, только GitHub;
- сервис и страница результата живут на MacBook (loopback); для удалённых пользователей нужен HTTPS-endpoint;
- браузерный сценарий фиксированный и написан под веб-демо;
- агент-писатель тестов для любого стека реализован в последних коммитах; live-приёмки в документах пока нет — M6 проходил с предыдущей генерацией C#-тестов;
- в режиме `agent` покрытие разбирается только из Cobertura (LCOV, JaCoCo — нет).

**Следующие шаги (по [phases.md](phases.md) и [ADR 0001](decisions/0001-mvp.md)):** несколько проектов и стеков, облачный запуск, GitHub App вместо self-hosted runner, комментарии в PR, интеграция с трекером, исследовательский браузерный агент, управление библиотекой тестов и flaky-тестами, GitLab.

## 13. Предлагаемая структура слайдов

1. **Проблема** — тесты на новое требование не пишутся, ручной QA медленный (раздел 2).
2. **Решение в одной фразе** + демонстрация потока push → зелёный/красный job → QA-ветка (разделы 1, 3).
3. **Конвейер M1–M4** — схема из раздела 4.
4. **Где работает ИИ, а где код** — таблица из раздела 5 + принцип «LLM предлагает, код решает» (6.1).
5. **Защита от галлюцинаций** — проверки агента-писателя, повтор без сгенерированных тестов, честные статусы (6.2–6.4).
6. **Браузер** — скриншот формы, trace, desktop/mobile (раздел 8). Можно показать видео M5 из `artifacts/m5-acceptance/m5-presentation.mp4`.
7. **Живая демонстрация / кейс M6** — дефект с пробельным паролем: 7 тестов упали → исправление → 84/84, 95,65% покрытия изменений (раздел 9).
8. **Агент сам нашёл свои баги** — три исправления из live-приёмки (раздел 9).
9. **Безопасность** — изоляция, секреты, недоверенные данные (раздел 10).
10. **Архитектура и стек** (разделы 6.6–6.7, 11).
11. **Ограничения и roadmap** (раздел 12).
