# План MVP и приёмка

## Последовательность на 15 часов

| Время | Работа | Проверяемый результат |
| --- | --- | --- |
| 0–2 ч | Демопроект, ТЗ с ID, стартовые тесты, Docker, API-ключ | Проект и тесты запускаются одной командой |
| 2–5 ч | GitHub Actions, локальный сервис, PostgreSQL, точный diff | Push создаёт запуск на нужном SHA |
| 5–8 ч | LLM-анализ, план, генерация тестов, исправление ошибок генерации | Новая фича получает исполняемые тесты |
| 8–11 ч | Полный прогон, Playwright, screenshots и traces | Внесённая ошибка воспроизводится |
| 11–13 ч | QA-ветка, Markdown, простая страница | Результат виден в браузере и GitHub |
| 13–15 ч | Два последовательных обновления, стабилизация, запись | Полный цикл проходит дважды |

Каждый пласт работы оформляется отдельным Conventional Commit с коротким телом «что и зачем». Перед каждым commit выполняется полный набор проверок командой `bash scripts/check.sh`: форматирование, анализаторы, сборка с проверкой типов/зависимостей и все тесты. После завершения функциональности проводится независимая проверка тестами и ревью кода. В М0 уже есть базовые unit- и интеграционные тесты архитектуры.

## Демонстрация

1. ТЗ описывает регистрацию, запрет повторного email и доступ к собственному кабинету.
2. Push новой фичи с ошибкой обработки повторного email автоматически создаёт запуск.
3. Агент добавляет тесты, воспроизводит дефект в браузере и публикует QA-ветку с отчётом.
4. Разработчик принимает тесты и исправляет продукт.
5. Следующий push сохраняет эти тесты, выполняет всю базу и подтверждает исправление.

## Условия приёмки

- Push с несколькими коммитами проверяет весь диапазон, а повтор события возвращает прежний запуск.
- Push в `qa/**` и изменение только отчётов не запускают проверку; при следующем push старый запуск не меняет `headSha`.
- Первый запуск требует явного `baseSha`; недоступный SHA даёт понятный `BLOCKED`.
- LLM-ошибка, ошибка генерации тестов и недоступный стенд не дают `PASSED`.
- Старые и новые тесты выполняются вместе; тесты-кандидаты не теряются и не объявляются принятыми до слияния.
- Отчёт содержит требования, diff, тесты, line coverage изменений, воспроизведение, screenshot/trace, длительность и LLM-расход.
- Контейнеры не видят токены, домашнюю папку и Docker socket. В Git нет реальных `.env` или секретов.

Оценка «50–60% полного продукта» не используется: глубина автономности и поддерживаемые стеки определяются после MVP.
